Excel / VBA: Working Prototype

MaterialFlow

Traceable material-request and dispatch management for distributed construction sites.

Project type

Independent operational system, developed from a real technical-office workflow

Role

Workflow analysis, process design, workbook architecture, VBA automation, interface design

Primary users

Site engineers, technical-office teams, material coordinators, warehouse personnel

Development status

Technical workflow completed; not organisationally rolled out because I moved into a new role before adoption began

Core technologies

Microsoft Excel, VBA, structured worksheets, data validation, automated PDF export, local file-based archiving

01

Overview

MaterialFlow is a material-request and dispatch-management system built for construction projects operating across multiple sites and locations. It was designed to replace inconsistent request documents and fragmented material-tracking files with a single controlled workflow.

Users prepare requests through a structured Excel interface. The system validates the information, generates a unique request number, produces a formal request document, exports it as a PDF, and records each requested item in a central archive. As materials are dispatched, the system records delivered quantities and calculates what remains outstanding, while keeping the familiar Excel environment project teams already used.

02

The problem

Material requests from distributed sites were typically communicated through independently prepared Excel files, handwritten forms, email attachments, calls, and informal lists. Even where a standard form existed, information was entered differently by each project or person. In practice this produced:

  • inconsistent request formats and incomplete project or location information
  • duplicated requests and unclear document numbering
  • difficulty identifying the latest version of a file
  • a weak link between requests and dispatch records
  • uncertainty about how much material remained outstanding
  • repeated manual preparation of formal documents

A material request is not just a document; it is an operational record that has to stay consistent as it moves between site teams, the technical office, the warehouse, and management.

03

Design challenge

How can material requests be standardised and made traceable without requiring project personnel to learn an unfamiliar enterprise platform?

A fully manual Excel process preserves familiarity but gives up consistency and history. A new standalone platform offers stronger data control, but introduces training requirements, new logins, and implementation resistance. This is the classic tension this whole research interest is built around. MaterialFlow took an incremental approach instead: keep Excel as the user-facing environment, but place controlled fields, automation, document generation, and central tracking around it.

04

Core workflow

User creates material request ↓ Project and location information selected ↓ Material, unit and quantity entered ↓ Required fields validated ↓ Unique request number generated ↓ Formal request document populated ↓ Request line items written to central archive ↓ PDF generated and stored ↓ Material dispatch recorded ↓ Outstanding quantity recalculated

The printable document and the tracking record are generated from the same source information, which removes the need to enter identical data twice into separate files.

05

Key capabilities

Standardised request creation

A consistent request structure, covering project, location, discipline, material, unit, quantity, delivery requirement, and notes, reduces the variation technical-office teams previously had to reconcile by hand.

Request numbering and formal document generation

Each completed request receives a structured number, supporting search, referencing, and linking requests to dispatch records without ambiguous filenames. Entered data is transferred automatically into a printable template; no manual copying from an entry table into a separate form.

Central line-item archive

Every material within a request is written into the archive as an individual structured row, so a request can be read both as a formal document and as searchable operational data, filterable by request number, project, location, date, material, and dispatch status.

Dispatch and outstanding-quantity tracking

Dispatched quantities are recorded against the original request; outstanding quantity is calculated as requested minus dispatched, so a request stays visible until fully delivered, whether fulfilled in one delivery or several partial ones.

06

Architecture

Excel/VBA workbook | |-- User-facing request interface | |-- Project selection | |-- Location-dependent fields | `-- Material, quantity, delivery entry | |-- VBA automation layer | |-- Validation, numbering, template population | |-- Archive insertion and search | `-- PDF generation and file naming | |-- Central data layer | |-- Request archive / dispatch records | |-- Outstanding quantities | `-- Material master data | `-- Output layer |-- Printable request form `-- PDF archive

07

Key design decisions

  • Excel as the adoption layer: built inside a tool project and technical-office staff already knew, so people could benefit without learning a new interface first.
  • One source for document and data: the formal request and the archive record come from the same input, removing the risk of the sent document and the tracked record drifting apart.
  • Traceability beyond document creation: the workflow keeps following a request through dispatch and remaining quantity, not just to the point the PDF is generated.
  • Familiar interface, stronger governance: key actions moved from unrestricted cell editing into controlled procedures: required fields, controlled lists, structured records, protected system areas.

08

Current status and limitations

Technically complete; not organisationally deployed

MaterialFlow's technical workflow was finished and demonstrated the intended automation end to end. Wider organisational rollout and any real measurement of adoption or time savings did not happen, because I moved into a new role before that rollout began. I consider that gap, a working tool that never became an adopted routine, one of the more useful things the project taught me, not something to round up or smooth over.

  • dependence on a macro-enabled Excel workbook and local file paths
  • no central database, user authentication, or role-based permissions
  • limited simultaneous multi-user access; possible version conflicts between copies
  • no ERP, accounting, or procurement integration
  • no formal usability study or measurement of error reduction

09

Reflection

MaterialFlow began as an attempt to standardise a request format. The deeper problem turned out to be the movement of information between people: who owns the process, how project-specific differences are represented, when a request should count as complete, whether familiar tools can support stronger organisational control.

A perfectly formatted request form does not, by itself, provide visibility. Value emerges when information stays traceable across the whole workflow. A functioning tool is only one part of that; the rest depends on process ownership, management support, and who is responsible for keeping the workflow alive.

That gap between technical readiness and realised value is the thread that runs from this project into the research questions I want to study formally.
